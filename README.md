# 永远有多远？


> 我的初衷不是想把过去变回现在。

---

前阵子我想把几年下来的聊天记录存到本地。不是备份到云端，是想真正拿到文件：能搜，能读，能自己排版。

我以为这件事一个周末能做完。实际花了一周多，而且卡住的地方跟技术难度关系不大。没有一个平台愿意让你把东西完整拿走，你只能一个 App 一个 App 地去它自己的数据库里找。

下面是我试过的路、卡在哪里、后来怎么绕过去的。没有任何账号、设备、路径信息。

## 先说路线

能想到的办法就三种。

第一种是拿设备备份，自己在本地解开。这需要一台电脑、一份加密备份、一个备份密码。能拿到的是设备本地缓存过的内容，包括正文、时间、发送方、消息类型，还有删除标记。缺点是上限很硬：本地没有的，永远拿不到。

第二种是走接口抓取。这要账号保持在线登录，也见过现成项目直接调网页版接口。能拿到服务端完整历史，媒体也齐。但这类做法通常违反平台协议，账号有风控风险，接口一变就得重写。

第三种是越狱或 root 之后直接读缓存。能拿全，门槛也最高，还得有合适的设备。

我选了第一种。原因不复杂：它不碰账号、不联网、不需要对方配合，只动自己硬盘上的一个文件夹。代价是接受“不完整”。

## 备份，和解开备份

第一件事是重做备份，并且一定要勾选加密。

不加密的备份看起来也有东西，但很多 App 的数据库根本没进去。勾了加密之后有个反效果：文件清单本身也被加密了，那份清单可能有 GB 级。没有密码，你连“哪个文件属于哪个 App”都列不出来。

解密的链路本身不长。

先用密码跑两轮 PBKDF2 得到一个主密钥，用它去解包各个保护类的密钥。然后拿清单文件对应的那个类密钥，把清单解出来，得到一张普通的 SQLite 表，里面记着每个文件的路径、大小和加密信息。之后按路径取任意一个文件：清单里给了一个四字节的保护类和一段被包裹的密钥，解开它，用 AES-256-CBC 加零 IV 解密，按记录的大小截断。

写起来就这几步，实际有三个地方要小心。

一是清单文件有 GB 级，整个读进内存会炸，得按块解密再落盘。二是类密钥解一次就够了，缓存起来，之后解单个文件是毫秒级。三是密码不要落盘，也不要打印，跑的时候用环境变量传进去，脚本报错时也别顺手把密码带出来。

我一开始图省事，用了个现成的解密库，后来因为备份太大、内存撑不住，才自己重写了一份。这部分代码我整理成了 [iosbackup-decryptor](https://github.com/WhiteAshura/ios-backup-decryptor)，纯 Python，只依赖 PyCryptodome。它只干一件事，就是解开备份，剩下的都在下面。

## 怎么找到一个 App 的数据

解开之后没什么技巧，就是笨办法。

先把所有 domain 列出来，按 App 的包名定位到它的容器目录，然后在里面找 `.sqlite`。看到文件旁边有 `-wal` 和 `-shm`，说明这个库是活跃的，读的时候要么先处理未提交的 WAL，要么接受可能丢最后几条。

打开库之后先看 `sqlite_master`，表名一般能猜出来哪张是消息表、哪张是会话表。再看一眼行数和时间范围，排掉空表和模板表。

有一个办法很省时间：很多 App 除消息表之外还有一张全文索引表。拿它的命中条数跟消息表对一下，差得多就是有地方没解对，或者分片没合全。这个交叉校验帮我发现过两次漏解。

## 一个没想到的发现

有几个 App 的私信，我原以为只存在服务器上。结果本地库里是完整的。

字段还挺齐：消息 ID、会话 ID、发送方 ID、服务端时间、正文、消息类型、删除标记，还有一个会话内递增的序号。有这几样，就能排出一条正常的时间线，不需要碰任何接口。

也有反过来的情况。有个 App 把最关键的那个主消息库标成了“不备份”，备份做完之后那里只剩一个几十 KB 的残留文件。这种就只能认了。

## 各平台差别很大

同样是聊天记录，库的结构差得离谱。粗分下来有四种。

一种是单表搞定，正文、时间、发送方都在一张表里，直接读就行，最省事。

一种是分片。消息被拆成好几个 `message_N.sqlite`，得按会话 ID 合并。这里有个坑：分片之间的序号不一定连续，靠时间戳排序会把同一秒里的几条打乱，必须拿会话内序号当主排序键。

一种是主库不在，只剩全文索引。能捞到一些正文片段，但没有顺序，只能当辅助。

还有一种是本地只缓存了打开过的会话，删掉的、没点过的都没有。这种拿到的量会明显偏少，别指望完整。

## 踩过的地方

**媒体文件基本拿不到。** 图片、语音、视频的本体大多在 App 的缓存目录里，而设备备份默认不包含缓存目录。导出结果里全是 `[图片]`、`[语音 3.4s]` 这样的占位符。原始链接里存的 CDN 地址签名有效期一般一年左右，等你想起来去补，早就失效了。这件事事后没有办法补救，只能一开始就走另一条路线。

**删掉的消息可能还在。** 很多本地库只是把 `deleted` 字段置为一，正文原样保留着。我一开始加了过滤条件，后来去掉，改成单独输出一列做标记。这类消息往往才是想找回的那部分。

**新版工具不一定更好。** 我升级过一次导出工具，语音转文字全部消失了，只剩音频文件。好在旧的导出结果还留着，按时间和发送方匹配，把几千条文本补了回来。之后再升级工具，我都会先跑一遍跟旧结果对比。

**“完整”这两个字要慎说。** 有平台的私信正文存在服务端，App 只缓存你点开过的会话，还会淘汰。导出来的东西在这台设备上确实穷尽了，但不等于全部历史。写文档的时候我标的是“本设备缓存范围内的完整”。

**用昵称关联一定会出事。** 昵称会改，备注会改，不同的人还可能重名。跨平台合并的时候，我一开始拿备注名当键，结果同一个人冒出三份身份。后来统一用平台唯一 ID 做主键，昵称只用来显示。

**时间有四种存法。** 有的存 UTC 秒，有的存本地时间字符串，有的带毫秒，有的干脆只有日期。统一成“UTC 时间戳 + 原始字符串”两列之后才好排。排序不能只看时间，同一秒内要靠序号。

**空表很多。** 草稿表、失败消息表、待发送表，看着像有东西，实际都是零行。旧版本的数据库备份文件也有类似情况，十几 MB 但消息表是空的。这些都得手动排掉，不然会白高兴一场。

## 合并的时候

各平台导出的格式完全不一样，最后我统一成一张宽表，六列：平台、时间、发送方、类型、正文、有没有媒体。

合并之前有三件事必须做。

类型要归一。原始类型值每个平台各有几十种，不统一就没法统计。我归到文本、图片、语音、视频、表情、卡片、系统、通话这几类。

发送方要归一。统一成“我”和“对方”，同时保留原始 ID，否则判错一次后面全错。

去重。同一段对话可能同时存在于两个平台（迁移、转发、备份），得按平台加消息 ID 去重。不能按正文去重，重复的日常废话太多了。

做完这三步，才把几千个碎片变成一条能读的时间线。

## 数字很容易说错

统计下来至少有三个数，含义完全不同。

总条数包含表情、卡片、系统提示、通话记录。真实文字条数是剔除这些之后的。还有一个是“我发出的条数”，按发送方筛。

这三个数经常被混着用，我见过有人拿总数当“我们聊了多少句”。对外说之前最好先定清楚是哪个。

## 收尾

中间解出来的明文库、解密后的清单、合并用的中间 JSON，用完都删了。脚本留着，随时能重新生成。备份密码只在环境变量里过一手，不写日志也不写配置。

导出的东西里有别人的私人内容，自己看可以，别外传。要公开引用的话，人名、头像、时间、地点都得打码或者改写。
